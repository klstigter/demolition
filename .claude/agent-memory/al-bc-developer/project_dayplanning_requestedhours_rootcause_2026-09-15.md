**Final answer, after 5 earlier same-day investigation attempts (see [[project_cpo_section3_exclude_flip_2026-09-15]] for that saga) all chased the wrong layer:** table 50610 "Day Planning"'s own hours-calc pipeline (`CalculateWorkingHours()` → `CalculateRequestedWorkingHours()`/`CalculateAssignedWorkingHours()`/`CalculateRealizedWorkingHours()` → `"General Planning Utilities".DayPlanningFulFillment`/`GetWorkingMinutes`) is correct and was never the bug. The `OnValidate` triggers on `"Start Time Requested"`/`"End Time Requested"`/`"Non Working Minutes Requested"` (and the Assigned/Realized equivalents) all correctly call `CalculateWorkingHours()`. The real gap: **`table_50610_DayPlanning.al`'s `OnInsert`/`OnModify` triggers never call `CalculateWorkingHours()`** — so any code path that sets the time fields via direct field assignment (`:=`, not `Validate()`) and then just `Insert()`/`Modify()`s, skips recalculation entirely and persists a stale/zero Hours field next to a real time range.

**Do NOT "fix" this by adding `CalculateWorkingHours()` to `OnInsert`/`OnModify` unconditionally** — confirmed this would be a regression: `codeunit_50695_DayPlanningSequenceMgt.al`'s `InsertSequenceLine` (and similarly `codeunit_50610`'s `CreateDayPlanning` for pattern-generated lines) *deliberately* hand-computes a non-zero `"Requested Hours"` placeholder for sequence-generated lines that have NO `"Requested Resource No."` yet (resource assigned later via drag/drop) — because the official calc's `DayPlanningFulFillment` does `if ResourceNo = '' then exit;`, which always leaves hours at 0 when the resource is blank. An unconditional `OnInsert` recalc would silently zero out every one of these legitimate pending-assignment placeholders. This is a real, load-bearing design exception, not an oversight.

**Confirmed live via `mcp__ah_bc_mcp__List_DayPlannings_PAG50606`** (sampled ~145 rows across 3 different offsets in a 27,882-row table): every sampled row with populated Start/End Time Requested already had correct, matching Requested Hours AND a populated `requestedResourceNo` — demo-data rows are fine. `@odata.count` on this API page does NOT reflect the applied `$filter` (always shows total table count, 27882, regardless of filter) — don't trust it for filtered-subset sizing; also `eq 0`/`eq ''`/`lt 1` filters against `BlankZero`/blank fields returned zero rows even when populated rows with 0/blank clearly exist elsewhere (suspect NULL-vs-0 three-valued-logic + NULLS-LAST orderby behavior in this OData provider) — use `contains(field,'')` or unfiltered sampling instead when hunting blank/zero rows via this MCP tool.

**Two genuine, confirmed-live bug sites found by code inspection in `codeunit_50604_DHXDataHandler.al`** (both fixed 2026-09-15, both compile/build clean, NOT published this session per user cost-conscious request):
1. `onEventAdded` (~line 1907-1946) — creates a new Day Planning row when a resource-scheduler drag creates an event. Calls `DayPlanning.Validate("Assigned Resource No.", Res."No.")` (which DOES trigger `CalculateWorkingHours()` as an OnValidate side effect) — but `"Start Time Assigned"`/`"End Time Assigned"` are set via direct field assignment AFTER that validate call, so the recalculation ran while both times were still blank. Then `Insert(true)` with no further recalc. Fix: added `DayPlanning.CalculateWorkingHours();` right before `Insert(true)`, after all three inputs (resource + both times) are in place.
2. `OnEventChanged_Project` (~line 2070-2193, despite the name it operates on the Assigned side — this is the sift-left/right/up/down drag-reschedule handler for an EXISTING row) — sets `"Start Time Assigned"`/`"End Time Assigned"` via direct assignment then just `OldDayPlanning.Modify()`, no recalc at all. This means every drag-reschedule of an already-assigned event left `"Assigned Hours"` stale (from before the move) while the times moved to the new slot — a silent, ongoing source of exactly this mismatch class for EXISTING rows, not just newly-created ones. Fix: added `OldDayPlanning.CalculateWorkingHours();` right before `OldDayPlanning.Modify();`.
3. `OnEventChanged_Resource` (~line 1947-2068) was checked too — almost entirely commented-out dead code, no live bug there.

**Repair tool built:** `src/report/report_50662_RepairDayPlanningHours.al`, report 50662 "Repair Day Planning Hours" (ProcessingOnly, UsageCategory=Administration, `Permissions = tabledata "Day Planning" = rm`). RequestPage: Job No. filter / Job Task No. filter / Plan Date From-To / "Preview Only (Dry Run)" toggle (defaults to true — safe by default). Calls the SAME shared `DayPlanning.CalculateWorkingHours()` procedure per candidate record (no duplicated formula), compares old vs new Requested/Assigned/Realized Hours, and — critically — re-applies the same "blank Resource No. + previously-non-zero Hours" placeholder guard described above (restores the old value in that specific case) so it can never wipe out the sequence-generator's legitimate pending-assignment placeholders. Reports Scanned/Candidates/Fixed-or-Would-fix/Placeholders-preserved via `Message()`. Compiled + built clean (`al_compile`/`al_build` both zero errors, zero warnings) 2026-09-15; NOT published or run live this session — user explicitly wants to run/test it manually.

**How to apply:** If asked to touch Day Planning hours-calc again, remember `CalculateWorkingHours()` is intentionally NOT wired into `OnInsert`/`OnModify` — any new direct-field-assignment call site that sets Start/End Time fields must call it explicitly before saving, mirroring the two fixes above, rather than relying on the table trigger. If another live drag/drop flow (in this codeunit or elsewhere) is later found with the same "direct assignment then Insert/Modify, no recalc" shape, it's the same bug class — same fix. Don't recommend re-adding `CalculateWorkingHours()` to `OnInsert`/`OnModify` without re-confirming the sequence-placeholder exception is handled (either by gating on Resource No. being non-blank, or the same restore-guard used in report 50662) — it will otherwise reintroduce the exact regression avoided here.
