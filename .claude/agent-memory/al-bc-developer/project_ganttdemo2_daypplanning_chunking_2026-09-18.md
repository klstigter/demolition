Implemented chunked/paginated Day Planning loading for page 50620 "Gantt Demo DHX 2"'s resource panel Default (unfiltered) mode, per explicit user-approved design (not a bug fix - proactive resilience against slow-connection single-point-of-failure on one large ~7k-record transfer).

**Why:** Day Planning volume for the visible 5-week window grew ~3x (2,273 -> 7,388+) and keeps growing; one big background-task round trip is a single point of failure on unstable connections. Chunking degrades that to "progressively slower" instead of "nothing for 90s then timeout."

**What changed:**
- `codeunit_50613_GanttChartDataHandler.al`: new paged overload `GetDayPlanningsAsJson(AnchorDate; JobNo; JobTaskNo; Skip; PageSize; var HasMore)` alongside the untouched 3-arg version (kept separate, not factored, to avoid any risk to the existing verified 3-arg callers - a deliberate deviation from the task's "factor if you can" suggestion). Running index spans both the main range pass and the second (blank-Plan-Date/Placeholder-Date) pass; "candidate" = a record that would have produced JSON in the unpaged output (i.e., second-pass candidates are gated on JobTask.Get succeeding + Placeholder Date in range, same as the unpaged version's inclusion logic).
- `codeunit_50713_GanttBGResourcePanelData.al`: 'Default' mode branch now reads optional `DayPlanningSkip`/`DayPlanningPageSize` params (default 0/1000), only fetches Resources on Skip=0, returns `dayPlanningsHasMore`/`dayPlanningsNextSkip` via a local `BoolToParamText` (own copy, codeunits can't call a page's local procs).
- `page_50620_GanttDemo.al`: new vars `PendingDayPlanningsHasMore`/`PendingDayPlanningsNextSkip`/`PendingDayPlanningsIsFirstChunk` + scope-snapshot vars `ResourcePanelChunkJobFilter`/`ResourcePanelChunkJobTaskFilter`/`ResourcePanelChunkAnchorDate` (snapshotted at chunk 0 so a mid-sequence filter change doesn't corrupt later chunks). New local proc `EnqueueNextDefaultResourcePanelDayPlanningChunk(Skip)` called from `OnPollResourcePanelResult` when `PendingDayPlanningsHasMore` - re-arms `ResourcePanelTaskRunning := true` (since `OnPageBackgroundTaskCompleted` already cleared it per-chunk) and calls `NotifyResourcePanelTaskPending()` again for a fresh 30s poll budget per chunk.
- `GantttControl.controladdin.al`: `LoadDayPlanningsData` signature gained a second `IsFirstChunk: Boolean` param.
- `wrapper.js`: `LoadDayPlanningsData(json, isFirstChunk)` - isFirstChunk=true replaces (resets `_resourcePanelDayPlanningsAccumulator`/`window.DayPlanningsByTask`/`DayPlanningsStore`); false appends to the accumulator and re-`.parse()`s the full accumulated array each chunk (simpler/safer than a true incremental store API, still visually progressive). `ClearData` also resets the accumulator.

**Deviation found and handled:** `EnqueueDefaultResourcePanelReload` had NO `ResourcePanelTaskRunning` guard check/set even before this session (unlike `EnqueueFilteredResourcePanelReload`, which does) - the task brief assumed it existed ("stays as today"). Left as-is per literal instruction rather than adding new guard behavior beyond the task's scope; noted as a pre-existing gap, not introduced by this work. Also added `PendingDayPlanningsIsFirstChunk := true` to `EnqueueFilteredResourcePanelReload` (a new var this session added) so Filtered-mode loads correctly REPLACE rather than risk stale false-appends left over from an aborted Default chunk sequence - a minimal necessary addition, not a scope violation of "don't touch Filtered mode's behavior/logic".

**Live verification (2026-09-18, NL_Copy20240710 sandbox, company CRONUS NL):** Default reload delivered exactly 7414 Day Planning records across 8 round trips (7x1000 + 1x414), resources (213) sent once on chunk 0 only, poll stopped itself cleanly (not via 20-attempt timeout) confirming HasMore correctly went false. Filtered mode (task-bar click on Job 10000/Task 1050) unaffected: 15 records, 1 resource, filter icon shown, and correctly REPLACED the prior 7414-record Default set (not appended). Resetting back to Default via the panel's X button correctly restarted a fresh accumulator (clean 1000/2000/3000... progression, no 15+1000=1015 contamination). Zero new console errors introduced (same 19 pre-existing unrelated errors - BC telemetry CORS noise, cross-company 401s - before and after).
