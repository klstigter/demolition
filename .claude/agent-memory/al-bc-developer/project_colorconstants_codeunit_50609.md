**Consolidation refactor (2026-08-20):** `src/codeunit/codeunit_50609_VisualDefaultSettings.al`, codeunit 50609, is the ONLY place holding the Assigned/Free-Capacity/ExternalBorder/CapacityBorder color hex constants, the Daily/Weekly bar-chart width defaults, and the skill-bar 5-colour palette/`"Skill Code"."Bar Color"`-override logic used across the Daily/Weekly bar charts (`src/dhx/barchart_daily`, `src/dhx/barchart_weekly`) and the three scheduler pages (projectschedule/50621, resourceschedule_with_capacity/50706, poolresourceschedule/50600). NOTE: the codeunit was later renamed from `"Color Constants Opti."` to `"Visual Default Settings"` - some wrapper.js doc-comments still say the old name in places not touched by the 2026-08-26 pass; trust the .al file for the current name.

**Override-wiring completion (2026-08-26):** Every hardcoded color/width constant in this codeunit that represents a genuine single overridable setting now has a real "Daily Optimizer Setup" (table 50605) field backing it, and page 50654's "Reset to default" action actually works (was a `message()` stub before).

**Public API (codeunit 50609):**
- `GetCapacitySegmentColors(var AssignedColor, var CapacityColor, var ExternalBorderColor: Text)` - all 3 now resolve through ONE `ResolveCapacitySegmentColors` local proc / ONE `"Daily Optimizer Setup".Get()` call: Assigned ← `"Assigned Color"` else `AssColorTok` (#548235); Capacity ← `"Unassigned Capacity Color"` else `CapacityColorTok` (#2E75B6); ExternalBorder ← `"External Border Color"` (field 66, new) else `ExternalBorderColorTok` (#FF0000). ExternalBorderColor only visually matters on the Daily/Weekly "Requested vs Capacity" bar charts' over-capacity/"external" segment borders - the 3 scheduler pages fetch it via this same call but discard it (never put it in their JSON), so it has zero effect there.
- `GetCapacityBorderColor(): Text` (new) - a SEPARATE, unrelated setting from the above: borders the Capacity bar/event on the live scheduler-timeline pages (50706, 50600), not the bar charts. ← `"Capacity Border Color"` (field 67, new) else `CapacityBorderColorTok` (#C97F16). Own `Get()` call, not folded into `ResolveCapacitySegmentColors` (different consumers, different concept). Forwarded by codeunit 50662's new thin wrapper of the same name, called from page 50706/50600 ControlReady, sent as `"capacityBorder"` in their `SetBarColors` JSON - wrapper.js in both pages already had the `colors.capacityBorder` handler pre-existing/unfed, so this was a small, contained wire-up.
- `GetDailyBarChartWidth()`/`GetWeeklyBarChartWidth(): Integer` ← `"Bar Width (px) - Bar Chart"` (shared by both charts; 0 = "use chart's own default", not a real value - Reset-to-default sets this field back to 0, never to 50/45/60).
- `GetSkillBarColor(SkillCode: Code[10]; PaletteIndex: Integer): Text` - unchanged, `"Skill Code"."Bar Color"` override else fixed 5-colour palette; blank for `'CAPACITY'` marker.
- `GetResourceSchedulerDayPlanningPalette`/`GetResourceSchedulerCapacityPalette` (8-slot each) and `GetResourceSchedulerFallbackColor` (4-slot) - deliberately OUT of setup-field scope, doc-commented "index-to-value mapping is fixed and must not be reordered"; each already has its own separate override path (`"Skill Code"."Bar Color"` / "Planning Color Opt." records), not a Daily Optimizer Setup field.
- `GetDefaultAssignedColor/GetDefaultCapacityColor/GetDefaultExternalBorderColor/GetDefaultCapacityBorderColor(): Text` (new, thin public getters over the private `Tok` labels) - exist ONLY so page 50654's Reset-to-default action doesn't duplicate the hex literals. Underlying `Tok` labels stay `local`/private per this codeunit's convention of never exposing raw vars directly.

**Table 50605 "Daily Optimizer Setup" fields added 2026-08-26:** field 66 `"External Border Color"` (Text[20]), field 67 `"Capacity Border Color"` (Text[20]) - same style as the other color fields in the "// Bar Colors" block (Caption, `DataClassification = CustomerContent`). Both exposed on page 50654 in `group(Colors) > group(Capacity)`, same `OnAssistEdit` → `Page "Color Picker Lookup"` pattern as every other color field on that page.

**Page 50654 "Reset to default" action (real as of 2026-08-26):** Single `Confirm('...', false)` (default No) BEFORE any changes - Cancel/No = zero field changes, no Modify() call at all. On Yes: calls `CreateDemoData.CreateDailyOptimizerSetupDefault()` FIRST (now `procedure`, was `local procedure`, in `codeunit_50602_CreateDemoData.al` ~line 180 - it owns Base Calendar/Work Hour Template/Default Skill/Order Intake Nos/Work Order Nos, ensures referenced master data exists via its own `EnsureXxx` helpers, and does its own `Get()/Insert()/Modify()`), then `Rec.Get()` to re-fetch, THEN sets `"Resource Scheduler - List Type" := ::"By Resource Group"`, all 4 color fields via the new `GetDefaultXxx()` getters, and `"Bar Width (px) - Bar Chart" := 0`, ending in one final `Rec.Modify(true); CurrPage.Update(false)`. Deliberately does NOT touch `"Envelope Color"`/`"Envelope Border Color"`/`"Assigned High (%)"`/`"Requested High (%)"` - confirmed no default source exists anywhere in AL for these (pure wrapper.js CSS fallbacks / no-default-at-all), so inventing a reset value for them was explicitly ruled out.

**Callers forwarding into 50609 (unchanged shape from 2026-08-20, plus one new wrapper):**
- Codeunit 50662 `"Skill Capacity Analysis Mgt."` (weekly) - `GetCapacitySegmentColors` thin wrapper (all 3 scheduler pages call this, not 50609 directly) PLUS new `GetCapacityBorderColor` thin wrapper (added 2026-08-26, used only by page 50706/50600).
- Codeunit 50608 `"SkillCapacityAnalysisMgt.v1"` (daily) - unchanged, still forwards `GetCapacitySegmentColors` through 50662.
- Codeunit 50604 `"DHX Data Handler"`'s `ResolveRequestedColor` - unchanged, calls 50609's `GetSkillBarColor` directly.

**How to apply:** Any future scheduler/chart visual-default constant should get the same treatment ONLY if it's a genuine single overridable value (not a fixed multi-slot palette with an existing per-record override already). Add: (1) a `Text[20]`/appropriate-type field to table 50605 at the next free ID, (2) a thin `GetDefaultXxx()` getter in codeunit 50609 alongside the existing ones, (3) fold the resolution into the nearest existing `Get()`-sharing resolver if it's part of the same logical group (like ExternalBorderColor joined `ResolveCapacitySegmentColors`), or give it its own resolver if it's conceptually separate (like `GetCapacityBorderColor`), (4) wire it into page 50654's Colors group with the standard `OnAssistEdit`/`Color Picker Lookup` pattern, (5) add it to `ResetToDefault`'s field list. Never re-hardcode a literal default in more than one place - `codeunit_50602_CreateDemoData.al`'s `CreateDailyOptimizerSetupDefault()` is the analogous single-source pattern for the NON-visual setup fields (Base Calendar/Work Hour Template/Default Skill/No. Series) - it's `procedure` (public) specifically so page 50654 can call it instead of re-deriving 'DEMOCAL'/'BASIS'/'ELEKTR'/'OI'/'WO'.
