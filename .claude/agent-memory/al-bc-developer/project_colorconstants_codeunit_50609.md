**Consolidation refactor (2026-08-20):** New `src/codeunit/codeunit_50609_ColorConstantsOpti.al`, codeunit 50609 `"Color Constants Opti."`, is now the ONLY place holding the Assigned/Free-Capacity/ExternalBorder color hex constants and the skill-bar 5-colour palette/`"Skill Code"."Bar Color"`-override logic used across the Daily/Weekly bar charts (`src/dhx/barchart_daily`, `src/dhx/barchart_weekly`) and the three scheduler pages (projectschedule/50621, resourceschedule_with_capacity/50706, poolresourceschedule/50600). Pure refactor - every resolved color value renders identically to before.

**Public API:**
- `procedure GetCapacitySegmentColors(var AssignedColor: Text; var CapacityColor: Text; var ExternalBorderColor: Text)` - Assigned/Capacity overridable via `"Daily Optimizer Setup"."Assigned Color"`/`"Unassigned Capacity Color"` (safe boolean-context `Get()` - see [[dailyoptimizer-test-framework-setup]]-adjacent note below), else `AssColorTok` (#548235)/`CapacityColorTok` (#2E75B6); ExternalBorder always `ExternalBorderColorTok` (#FF0000, no setup field).
- `procedure GetSkillBarColor(SkillCode: Code[10]; PaletteIndex: Integer): Text` - `"Skill Code"."Bar Color"` override else cycles a fixed 5-colour palette (`#C55A11/#ED7D31/#F4B183/#F8CBAD/#FBE5D6`); blank for the literal `'CAPACITY'` marker (`CapacitySkillCodeTok`). SkillCode is deliberately `Code[10]`, not `Code[20]` - confirmed live via `al_symbolsearch` that base-app table "Skill Code"'s own `Code` field is `Code[10]`, so any Day Planning `Skill` (Code[20]) value that ever validated already fits; callers truncate via `CopyStr(SkillCode, 1, 10)`.
- Also holds `CapacityBorderColorTok` (#C97F16, documented constant only - no setup field overrides it, matches resourceschedule_with_capacity/poolresourceschedule's `--cap-color-border` CSS default).

**Callers now forward into 50609 rather than holding their own copy:**
- Codeunit 50662 `"Skill Capacity Analysis Mgt."` (weekly) - its own `GetCapacitySegmentColors`/`GetSkillSeriesColor` (local) are now thin wrappers into codeunit 50609. Kept the same name/signature deliberately - all 3 scheduler pages call `SkillCapacityAnalysisMgt.GetCapacitySegmentColors(...)` (codeunit 50662) directly from their `ControlReady` triggers and needed ZERO changes.
- Codeunit 50608 `"SkillCapacityAnalysisMgt.v1"` (daily) - its public `GetSkillBarColor` is now a thin wrapper into 50609 directly. Its `GetCapacitySegmentColors` still forwards through codeunit 50662 (not directly to 50609) - lower-churn since that call site already existed and 50662's own version is itself now just a forward, so results are identical either way.
- Codeunit 50604 `"DHX Data Handler"`'s `ResolveRequestedColor` (used by projectschedule/50621 and resourceschedule_with_capacity/50706's JSON payload building) now calls codeunit 50609's `GetSkillBarColor` directly (skips 50608) - it already had its own per-JSON-build memoization/palette-index bookkeeping (`SkillColorDict`/`NextPaletteIndex`) which stayed put; only the underlying single-color lookup target changed.

**JS-side (wrapper.js) comments added, no value changes except one:** `SERIES_COLOR_PALETTE` in barchart_daily/barchart_weekly wrapper.js is a SEPARATE, currently-dead generic-series fallback palette - do not conflate with 50609's skill palette. `--dp-color-assigned`/`--cap-color`/`--cap-color-border` CSS defaults in projectschedule/resourceschedule_with_capacity/poolresourceschedule wrapper.js now carry "source of truth: codeunit 50609" comments. One real value change: poolresourceschedule/wrapper.js's `--cap-color`/`--cap-color-border` CSS defaults were changed from stale `#D4EDDA`/`#28A745` to `#2E75B6`/`#C97F16` (matching resourceschedule_with_capacity) for consistency - functionally inert either way since `SetBarColors` is always called unconditionally on that page, so this never actually renders.

**How to apply:** Any future scheduler/chart color logic (new page, new chart) should call codeunit 50609 directly rather than adding a 4th duplicate copy. If codeunit 50662/50608's forwarding wrappers ever get in the way, they can be bypassed (call 50609 directly) - they exist purely to avoid page-level call-site churn, not because of any real dependency.
