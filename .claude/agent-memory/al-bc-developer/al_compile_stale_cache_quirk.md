---
name: al-compile-stale-cache-quirk
description: al_compile/al_getdiagnostics/al_build can report stale false-positive "missing" or "already declared" (duplicate object, phantom nonexistent source path) errors after rapid edits - fixes differ by variant, see body.
metadata:
  type: feedback
---

Observed in this project (2026-07-08): after several back-to-back edits to `codeunit_50602_CreateDemoData.al` and `codeunit_50604_DHXDataHandler.al` in the same session, `mcp__al__al_compile` (and `al_getdiagnostics` scoped by folderPath) repeatedly reported:
- `AL0185 Codeunit 'Create Demo Data' is missing` (in report_50600)
- `AL0118 The name '"Create Demo Data"' does not exist in the current context` (in page_50654)

...even though `al_getdiagnostics` scoped directly at the two edited files individually returned zero errors, and a full `mcp__al__al_build` (which actually generates the .app package) succeeded with 0 errors/0 warnings, repeatedly, with a fresh output timestamp confirming it wasn't serving a cached result.

**Why:** `al_compile` appears to run against an incremental/cached in-memory compiler session that can get stuck referencing a stale project state after rapid consecutive edits across multiple files in one session. `al_build` does a full/cold compile and is authoritative — it's what actually produces the deployable package.

**How to apply:** If `al_compile` or `al_getdiagnostics` reports errors that look inconsistent (e.g. "object X is missing" for an object that demonstrably exists and compiles cleanly on its own), don't trust it blindly — cross-check with a full `al_build`. If `al_build` succeeds cleanly (0 errors/warnings, fresh timestamp), treat the build as ground truth and proceed (report the discrepancy to the user rather than silently chasing a phantom error). Don't burn time re-editing working code to chase an `al_compile`-only error that `al_build` doesn't reproduce. This does NOT excuse skipping `al_getdiagnostics`/`al_compile` as a first-pass check — just don't treat a lone `al_compile` failure as gospel when `al_build` disagrees.

**Second variant, opposite symptom (2026-08-06):** after editing `src/dhx/barchart/*.al` (codeunit 50662, page 50692), both `al_compile` AND `al_build` (not just `al_compile`) reported ~19 duplicate-object errors (AL0197/AL0264) all citing a SECOND copy of each file under a sibling path `src\dhx\barchart copy\...` — a folder that verifiably does NOT exist on disk (confirmed via `Glob`, `Bash ls`, and `PowerShell Get-ChildItem -Force` on the parent `src\dhx\` — only real folders like `barchart`, `barchart_v1` etc. were listed, no `barchart copy`). Re-running `al_compile`/`al_build` repeatedly reproduced the identical phantom-path errors every time (not the earlier variant's "one-off then clean" pattern) — this is a case where even `al_build` is NOT authoritative, contradicting the general rule above. `mcp__al__al_addproject` (re-adding the same project path) did NOT clear it either. What DID fix it: `mcp__al__al_downloadsymbols` with `force: true` (even with `globalSourcesOnly: true`, no server/company args needed) — after that, both `al_compile` and `al_build` immediately went clean (0 errors). Root cause undetermined (likely a stale in-memory project/file-enumeration snapshot on the MCP server's side that symbol re-download happens to invalidate as a side effect), but the phantom path pattern (`<realfolder> copy`) plus "duplicate object already declared" is the recognizable signature.
**How to apply:** If `al_compile`/`al_build` reports "already declared by the extension" errors citing a source path that doesn't exist on disk (verify with `Glob`/`Get-ChildItem -Force` before assuming it's real), don't chase it as a real duplicate-object bug and don't waste time re-adding the project via `al_addproject` — go straight to `mcp__al__al_downloadsymbols` with `force: true` (a plain `globalSourcesOnly: true, force: true` call is enough, no auth/company params needed) and recompile.

**Third variant (2026-08-20):** after editing `codeunit_50604_DHXDataHandler.al`, `page_50621`, and `page_50706` to read fields from table "Daily Optimizer Setup" (fields 60-65, confirmed present by directly reading the table source), `al_compile` reported ~31 `AL0132 'Record "Daily Optimizer Setup"' does not contain a definition for '<field>'` errors spanning BOTH the files just edited AND two untouched pre-existing pages (`page_50654_DailyOptimizerSetup.al`, `page_50678_ResourceSchedulerSetup.al`) that reference the same/sibling fields. Re-ran `al_getdiagnostics` scoped by `folderPath` AFTER a fresh, successful `al_build` (fresh timestamp confirmed via `ls`) — it reproduced the EXACT SAME 31 stale errors, unchanged. So unlike the first variant's implication that `al_getdiagnostics` scoped narrowly is a reliable cross-check, here even a full-folder `al_getdiagnostics` call issued strictly after a clean `al_build` still served the pre-build stale list — the diagnostic cache does not appear to invalidate on `al_build` success at all in this MCP server. `al_downloadsymbols force:true` was attempted first here and failed outright (`Downloaded 0 of 2` — server unreachable), so that fix path wasn't available/tested this time; `al_build` succeeding was the only usable signal.
**How to apply:** Treat a clean `al_build` (succeeded:true, 0 errors, fresh output timestamp) as sufficient proof of a working compile on its own — do NOT additionally require `al_getdiagnostics`/`al_compile` to also go clean before reporting success, since they may never clear in-session even after the real build is fine. Only escalate/investigate further if `al_build` itself fails.

**Fourth occurrence, same session (2026-08-20), with definitive proof technique:** immediately after creating new codeunit 50609 "Color Constants Opti." and repointing codeunit 50662/50608/50604 to call into it, `al_compile`/`al_getdiagnostics` reported `AL0185 Codeunit 'Color Constants Opti.' is missing` at the new call sites PLUS the exact same recurring `page_50654_DailyOptimizerSetup.al`/`page_50678_ResourceSchedulerSetup.al` field-missing errors from the third variant above (unrelated files, not touched this task either) - `al_build` succeeded cleanly both before and after a repeat run. Got airtight proof this time: `al_getdiagnostics` cited `page_50678_ResourceSchedulerSetup.al` errors at lines 23/28/33/38/52/57/67/72, but `Read`-ing that file on disk showed it is only 42 lines total - the cited line numbers don't exist in the current file at all. This is conclusive: the diagnostics tool is serving output from some earlier/different version of the file, not the current disk state - not a subtle caching nuance, a flatly wrong snapshot.
**How to apply:** When `al_compile`/`al_getdiagnostics` errors look suspicious (missing object/field that you've directly confirmed exists in the source), a fast high-confidence check is to `Read` the cited file and see if it even has that many lines / that content at all - if the citation is out of range or unrecognizable, that alone proves staleness without needing to re-run anything. Then just rely on `al_build`'s result as usual.
